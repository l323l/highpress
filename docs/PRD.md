# 축구 칼럼 앱 PRD

v2 · Oct 8, 2026 (v1 Oct 5, 2026) · @lee


## 1. 개요

- 제품: 축구 칼럼 작성 유틸리티 툴 (글쓰기 + 스탯 조회 + 영상 컷편집 + 전술 모션그래픽)
- 배포 형태: 설치 없이 브라우저에서 쓰는 웹앱. 로그인 없이도 기기 저장으로 쓸 수 있고, Google로 로그인하면 초안 동기화와 스탯 조회가 켜짐 (누구나 가입, 가입자 상한 있음)
- 저장 원칙: 사용자 기기(브라우저 저장소)가 원본. 서버에는 작성 중 초안의 텍스트만 동기화하고, 사진·영상·GIF는 올리지 않음
- 대상 사용자: 축구 칼럼 작성자 (다수)
- 결과물: 1차는 네이버 블로그·카페에 복사·붙여넣기, 2차에 네이버 카페 직접 게시(API) 추가

### 2.1 목표 규모와 성공 지표

| 항목 | 기준 (안) | 상태 |
| --- | --- | --- |
| 1차 출시 대상 | 로그인 없는 공개 웹앱 (서버 자원을 쓰지 않으므로 인원 제한 없음) | 가정 |
| 2차 가입 방식 | 누구나 가입 (Google 로그인). 가입자 상한(기본 50명)과 80% 판정 기준으로 무료 한도를 보호 | 확정 |
| 2차 베타 목표 인원 | 50명 | 가정 |
| 지표 1: 칼럼 완성률 | 작성을 시작한 칼럼 중 `저장`까지 간 비율 60% 이상 | 가정 |
| 지표 2: 작성 소요 시간 | 전술 애니메이션 1개 포함 칼럼 1편을 기존 방식(여러 툴 사용)보다 짧게. 기준값은 1차 출시 후 요청자 실사용으로 측정 | 가정 |
| 지표 3: 붙여넣기 성공률 | 네이버 에디터에 붙여넣은 뒤 서식 수정 없이 게시 가능한 비율 (M0 실측으로 기준 확정) | 가정 |

- 지표는 서버 수집 없이 측정 가능한 범위로 한정 (광고·추적 도구 미포함 원칙, SEC-11). 1차는 요청자 실사용 기록, 2차는 서버의 초안 생성·삭제 횟수만 사용.

## 3. 필수 제약

| 제약 | 적용 방식 |
| --- | --- |
| 완전 무료 | 오픈소스 라이브러리 + 결제수단 등록이 필요 없는 무료 플랜만 사용 (Supabase Free, 무료 정적 호스팅, 무료 서브도메인) |
| 종량제 금지 | 무료 한도 초과 시 과금이 아니라 차단되는 서비스만 허용. 유료 플랜 업그레이드 경로를 전제로 설계하지 않음 |
| 보안 취약 요소 제외 | 비공식 스크래핑 제외, 비밀 키는 서버 쪽에만 보관, 사용자별 접근 통제(RLS) 필수, 사진·영상은 서버로 올리지 않음 |
| 무료 한도 = 서비스 규모 상한 | 사용자별 할당량, 서버 캐시, 자동 삭제로 한도 안에 유지 |

## 4. 핵심 사용 흐름

1. 접속 → 홈(내 칼럼 리스트). 2차부터 소셜 로그인 후 진입
2. 우측 하단 원형 글쓰기 버튼 → 글쓰기 화면 (글쓰기 툴만 표시). 초안은 기기에 자동 저장. 2차부터 초안 텍스트를 서버에 지연 동기화
3. 상단 탭의 `모션` 클릭 → 글쓰기 창 옆에 모션그래픽 창 열림 → 경계선 드래그로 크기 조절, 두 창 동시 작업 → 드래그 앤 드롭으로 본문에 삽입
4. (2차) `스탯` 탭 → 검색(서버 캐시 경유) → 표/카드로 본문에 삽입
5. (2차) 영상 파일 불러오기 → 브라우저 안에서 구간 자르기·배속·음소거 → 결과 파일 내려받기
6. `저장` → 글+사진을 기기 저장소에 완료 상태로 기록 → (2차) 서버의 초안 삭제
7. 내보내기 → 1차: 서식 유지 복사 + 미디어 일괄 내려받기 → 네이버 에디터에 붙여넣기 / 2차: 초안 강제 저장 → 네이버 로그인(팝업) → 카페 게시(API) → 임시 미디어 정리

## 5. 기능 요구사항

**출시 단계 표기**: `1차` 로그인 없는 기기 저장 버전 (M0\~M3) / `2차` 계정·서버·스탯·영상·카페 게시 (M4\~M9) / `후순위` 그 이후 (M10)

- 원안은 거의 전 항목이 P0였음. 핵심 가치(칼럼 1편 완성)를 먼저 검증하기 위해 1차 범위를 에디터 + 전술판 + 복사·붙여넣기로 축소함.

- 영상·GIF 등 미디어는 보관하지 않음.

### 5.3 영상 편집 툴

| ID | 요구사항 | 출시 단계 |
| --- | --- | --- |
| V-1 | 로컬 영상 파일 불러오기 (mp4, mov, webm) | 2차 |
| V-2 | 타임라인에서 시작·끝 지점 지정 후 구간 자르기 | 2차 |
| V-3 | 여러 구간 잘라 이어붙이기 | 후순위 |
| V-4 | 재생 속도 변경 (0.25x \~ 4x) | 2차 |
| V-5 | 소리 제거 (음소거 토글) | 2차 |
| V-6 | 미리보기 재생 | 2차 |
| V-7 | 내보내기: mp4, GIF → 결과 파일 내려받기 | 2차 |
| V-8 | 전 과정 기기 내 처리 (외부 업로드 없음) | 2차 |

- 영상은 브라우저 안에서만 처리하고 서버로 보내지 않음 → 서버 비용·용량 영향 없음.
- 처리 경로 (7장 참조): 전부 WebCodecs(mediabunny)로 처리. 재인코딩이 필요한 작업(배속, GIF, 정밀 구간 자르기)과 재인코딩 없는 구간 자르기("원본 그대로") 모두 같은 라이브러리가 맡음. ffmpeg.wasm은 쓰지 않음.
- 배속 시 소리 처리: 제거로 확정. 소리는 원래 속도(1x)에서만 유지.
- 브라우저 처리 한계와 상한(M0 실측으로 확정): 파일 2GB, 구간 5분, 결과 길이 10분, GIF는 결과 15초(가로 480, 초당 10장). MP4 기본 화질은 720p(1080p는 실시간의 약 0.6배 속도라 느림).
- 영상 저작권(중계 영상 사용)은 사용자 책임임을 약관에 명시. 앱은 영상 다운로드 기능을 제공하지 않음.

- 조작 원칙: 타임라인 곡선 편집 없음. "장면 추가 → 드래그" 반복만으로 완성.

## 7. 시스템 구조

- 형태: 웹앱(PWA) + 무료 정적 호스팅. 2차부터 Supabase 무료 플랜 추가 (인증, DB, Edge Function)
- 1차는 서버 없이 정적 호스팅만으로 동작
- 설치형 데스크톱 앱을 제외한 이유: 공개 배포 시 코드 서명 비용(Apple 개발자 등록 등)이 발생하고, 미서명 앱은 보안 경고가 뜸
- 브라우저(사용자 기기): 에디터, 전술판, 영상 처리, 작성 중 초안과 저장 완료된 칼럼(글+사진), 모션 프로젝트 데이터
- Supabase (2차): 계정, 작성 중 초안의 텍스트 사본, 스탯 공용 캐시, 호출 예산 카운터
- Edge Function (2차): 축구 API 프록시, 네이버 토큰 교환·카페 게시 중계 (비밀 키 보관 위치)
- 서버에 두지 않는 것: 사진, 영상, 렌더링된 GIF, 저장 완료된 칼럼

| 전술판 | Konva.js (Canvas) | 드래그, 키프레임 보간 |
| 기기 저장 | IndexedDB / OPFS | 브라우저 저장소. 백업 파일 내보내기·가져오기 제공 |
| 파일 내보내기 | 내려받기(ZIP) / File System Access API | 후자는 Chrome·Edge 한정 선택지 |
| 인증 (2차) | Supabase Auth (소셜 로그인) |  |
| 서버 DB (2차) | Supabase Postgres | RLS 필수. Storage는 사진 동기화를 채택한 경우에만 사용 |
| 서버 로직 (2차) | Supabase Edge Functions | 축구 API 프록시, 네이버 중계 |
| 정기 정리 (2차) | Supabase 예약 작업(pg\_cron) | 만료 초안·캐시 삭제, 사용량 기록 |

- FFmpeg 라이선스: ffmpeg.wasm을 쓰지 않으므로 해당 없음. mp4 인코딩은 브라우저 내장 코덱(WebCodecs)을 씀.
- 브라우저 저장소는 사용자가 브라우저 데이터를 지우면 사라짐 → 백업 내보내기 안내 필수.

### 7.1 Supabase 초안 동기화 (2차, 무료 플랜)

**원칙**: 기기 저장소가 원본. 서버 초안은 다른 기기에서 이어 쓰기 위한 텍스트 사본.

**흐름**: 글쓰기 시작 → 기기에 자동 저장(10초 이하) → 변경이 있으면 30\~60초 지연 후 본문 텍스트를 서버 초안 행에 전송 → `저장` 클릭 → 글+사진을 기기에 완료 상태로 기록 → 기록 성공 확인 → 서버의 초안 행 삭제

| ID | 요구사항 | 출시 단계 |
| --- | --- | --- |
| SB-1 | `drafts` 테이블(초안 본문 텍스트), 사용자 ID별 RLS. 사진은 올리지 않고 본문에 자리표시만 남김 | 2차 |
| SB-2 | 기기 저장소가 원본. 서버 전송은 변경이 있을 때만, 마지막 입력 후 30\~60초 지연. 화면 이탈·`저장` 시 즉시 전송 | 2차 |
| SB-3 | 기기 저장이 성공한 것을 확인한 뒤에만 서버 초안 삭제 | 2차 |
| SB-4 | 삭제 실패 시 재시도, 고아 데이터 정기 정리 | 2차 |
| SB-5 | 사진·영상·GIF는 서버에 올리지 않음 | 2차 |
| SB-6 | 사용자별 할당량 (안): 초안 3개, 초안 1개당 본문 1 MB. 서버 측에서 강제(DB 제약·트리거), 초과 시 동기화 거부 | 2차 |
| SB-7 | 방치 초안 자동 삭제 (안): 7일간 수정 없으면 서버 사본 삭제, 삭제 전 앱 내 안내. 기기의 원본은 유지 | 2차 |
| SB-8 | 다른 기기에서 초안을 열면 사진 자리에 "원래 기기에만 있음" 표시, 그 자리에 사진을 다시 넣을 수 있음 | 2차 |
| SB-9 | 서버 접속 불가(프로젝트 일시정지 포함) 시 기기 모드로 계속 작성. "서버 점검 중 — 글은 이 기기에 저장됩니다" 안내 화면 표시, 복구되면 자동으로 동기화 재개 | 2차 |
| SB-10 | 80% 판정 기준(5.6) 도달 시 신규 가입·신규 초안 동기화 제한 | 2차 |

**사진 동기화를 채택하는 경우 (조건부, 14.2 ① 결정에 따름)**

| ID | 요구사항 |
| --- | --- |
| SB-11 | 브라우저에서 Storage로 직접 올리지 못하게 차단. Edge Function이 사용자 합계 용량을 확인한 뒤에만 서명 업로드 URL 발급 |
| SB-12 | 사용자별 사진 합계 30 MB. 발급 시점에 UserUsage로 확인, 업로드 완료 후 실제 크기로 갱신 |
| SB-13 | 업로드 전 리사이즈·압축, 이미지 형식·크기 서버 측 검증 |

**무료 플랜 한도 (2026년 검색 기준, 가입 시 공식 요금 페이지 재확인)**

| 항목 | 한도 (전체 사용자 합산) | 영향 |
| --- | --- | --- |
| DB | 500 MB | 초안 텍스트 + 스탯 캐시. 사용자당 최대 3 MB(초안 3개 × 1 MB) → 베타 50명이 전부 채워도 150 MB |

| 전송량 | 월 5 GB | 텍스트·스탯 응답만 오가므로 사진 동기화 대비 부담이 작음 |
| 월간 활성 사용자 | 50,000명 | 여유 |
| Edge Function | 월 50만 회 | 스탯 조회·게시 중계. 여유 |
| 결제수단 | 불필요 | 미등록 상태에서는 과금 불가. 초과 시 서비스 제한 |
| 일시정지 | 1주일 미사용 시 자동 정지, 수동 복구 | 7.4 참조 |

- 텍스트만 동기화하면 저장소·전송량 제약이 크게 줄어듦. 수용 인원 상한은 베타 운영 중 실제 사용량으로 다시 산정.

### 7.2 API-Football 캐싱 검토

**결론**: 배포 구조에서는 서버 캐싱이 필수이며 실효가 큼. 키 1개의 일 100회를 전체 사용자가 나눠 쓰므로, 캐시 없이는 사용자 몇 명만으로 소진됨. 캐시가 있으면 같은 데이터는 하루에 정해진 횟수만 호출하므로 사용자 수와 무관해짐.

| 항목 | 서버 캐시 없음 | 서버 캐시 있음 |
| --- | --- | --- |
| 호출 수 결정 요인 | 사용자 수 × 조회 수 | 조회되는 데이터 종류 수 |
| 사용자 50명이 같은 순위표 조회 | 50회 | 1회 |
| 종료된 경기 상세 | 조회마다 호출 | 최초 1회 후 영구 재사용 |
| API 키 위치 | 앱에 노출 | 서버에만 보관 |

| 구성 요소 | 내용 |
| --- | --- |
| 프록시 | Edge Function이 요청을 받아 캐시 확인 → 없을 때만 축구 API 호출 → 결과 저장 |
| 캐시 저장소 | Supabase 테이블 (요청 키, 응답, 만료 시각) |
| 예산 카운터 | 일일 호출 수 기록. 잔량이 적으면 우선순위 낮은 요청(선수 상세 등) 차단 |
| 사용자 제한 | 로그인 사용자만 호출, 사용자별 분당·일일 조회 제한 |
| 정리 | 만료된 캐시 정기 삭제. 종료 경기 상세는 용량 상한을 두고 오래된 것부터 삭제 |

**한계**: 캐시는 중복 호출만 줄임. 사용자들이 서로 다른 리그·경기·선수를 폭넓게 조회하면 일 100회로 부족 → 지원 리그를 제한(예: 주요 5개 리그)하고 기본 데이터는 football-data.org로 분산. 그래도 부족하면 사용자가 본인 무료 키를 입력하는 방식을 선택지로 둠 (14.2 ④).

**캐시 정책 (어느 쪽이든 동일)**

| 데이터 | 보관 기간 |
| --- | --- |
| 종료된 경기 상세(라인업·이벤트·스탯) | 무기한 (변하지 않음) |
| 리그·팀·시즌 목록 | 시즌 단위 |
| 순위표 | 6\~24시간 |
| 선수 시즌 스탯 | 24시간 |
| 일정 | 24시간 |

- 호출 절약: `/fixtures?ids=`로 여러 경기 상세를 1회에 조회.
- 고정 소모 예시(추정): 5개 리그 순위표를 하루 4회 갱신 = 20회. 나머지 80회가 경기 상세·선수 스탯 몫.

**캐싱으로 해결되지 않는 것**

- 무료 플랜의 시즌 범위 제한: 공식 안내는 "최근 시즌 제공", 다른 출처는 일부 시즌 접근 거부 사례를 언급 → 현재 시즌 조회 가능 여부를 **M4에서 실제 키로 확인**. 불가하면 API-Football은 탈락.
- 약관상 데이터 저장·재게시 조건 → 가입 시 확인.

### 7.3 교차 출처 격리 헤더 (COOP/COEP)

**문제**: ffmpeg.wasm 멀티스레드 빌드는 교차 출처 격리(COOP `same-origin` + COEP `require-corp`)가 필요함. 이 헤더를 앱 전체에 걸면 다음이 깨질 수 있음.

| 영향 받는 기능 | 깨지는 이유 |
| --- | --- |
| 소셜 로그인·네이버 로그인 팝업 | 팝업과 원래 창의 연결이 끊겨 로그인 결과를 전달받지 못함 |
| 외부 이미지 (팀 로고, 선수 사진) | 외부 서버가 허용 헤더를 주지 않으면 표시 차단 |
| Supabase Storage 사진 (채택 시) | 동일 |

**M0 검증 항목**

1. 무료 정적 호스팅에서 경로별로 응답 헤더를 다르게 설정할 수 있는지
2. 격리 헤더를 건 상태에서 OAuth 팝업 로그인과 외부 이미지 표시가 동작하는지
3. WebCodecs만으로(격리 없이) V-2, V-4, V-7 목표 성능이 나오는지
4. ffmpeg.wasm 단일 스레드 빌드(격리 불필요)의 스트림 복사 속도

**결과 (2026-10-09 M0 실측)**: 1순위(격리 헤더 없음)로 확정. WebCodecs만으로 목표 성능이 나왔고 ffmpeg.wasm은 필요 없었음. 격리 헤더를 쓰지 않으므로 OAuth 로그인·외부 이미지와의 충돌도 없음.

**적용 순서**

| 순위 | 구성 | 채택 조건 |
| --- | --- | --- |
| 1 | 격리 헤더 없음: WebCodecs + ffmpeg.wasm 단일 스레드 | 검증 3, 4가 목표를 충족 |
| 2 | 영상 툴만 별도 경로(페이지)로 분리하고 그 경로에만 격리 헤더 적용. 에디터와는 브라우저 저장소(OPFS)로 결과물 전달 | 1이 성능 미달이고 검증 1이 가능 |
| 3 | 앱 전체 격리 | 검증 2가 통과한 경우에만 |

### 7.4 무료 프로젝트 일시정지 대응 (2차)

| 항목 | 내용 |
| --- | --- |
| 영향 | 정지 중에는 로그인, 초안 동기화, 스탯 조회, 카페 게시가 모두 중단. 기기 저장·전술판·영상 편집·복사·붙여넣기는 계속 동작 |
